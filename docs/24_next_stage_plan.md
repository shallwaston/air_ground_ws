# 24 Next Stage Plan

## 下一阶段建议目标

下一阶段建议继续沿着现有工程骨架和工具链自然推进，而不是立刻跳进真实双机和重型系统集成。

建议目标是：

- 在现有通信框架、接口契约和验收工具链基础上，继续把后续真实模块接入前需要的“接口准备、消费梳理、替换边界”整理清楚
- 保持当前单机、可复现、可验收的工作方式
- 为 FAST-LIO2、后续地图链路、UGV 导航和机械臂抓取的后续阶段做好工程入口准备

## 进入下一阶段前已具备的条件

当前已具备以下进入条件：

- 单机 mock 基线已通过
- 工程骨架已形成并可构建、可启动、可测试
- 真实点云样本驱动的局部、scan-aligned 2.5D MapTile 链路实验已打通
- benchmark / summary / QoS / 测试 / 文档已收口
- 阶段 4 已完成，`R0` 为主锚点，阶段 2 仅保留为辅助对照
- `R2` 已收敛为当前阶段 4、当前这条局部 MapTile 实验链路内的默认推荐参数组
- `R3` 已收口为基于 `R2` 的次要运行时验证结果，不替代 `R2`

## 当前承接前提

下一阶段计划必须建立在下面这些已收口前提上：

- 当前实验只能表述为“真实点云样本驱动的局部、scan-aligned 2.5D MapTile 链路实验”
- 当前实验不能表述为全局融合地图
- `R0` 是阶段 4 主锚点
- `R2` 是当前阶段 4、当前这条局部 MapTile 实验链路内的默认推荐参数组
- `R3` 是基于 `R2` 的次要运行时验证，不替代 `R2`

## 建议先做什么

建议下一阶段先做轻量、接口导向、可审阅的工作，而不是直接进入真实硬件和复杂部署：

- 先梳理当前局部 MapTile 链路的下游消费边界、输入输出契约和后续替换接口
- 先把未来 FAST-LIO2 / 后续地图链路接入时需要保持不变的 topic / frame / message / launch 边界梳理清楚
- 先明确下一阶段的验收口径、验收顺序和“做到什么算进入下一阶段”

## 下一阶段候选入口（按优先级）

### 优先级 1：继续完善局部 MapTile 链路下游消费 / 接口梳理

建议内容：

- 明确 `/uav/map/tile` 在当前工程骨架中的消费边界
- 明确 UGV 侧和后续模块对该消息的依赖方式
- 明确哪些语义属于当前实验结论，哪些语义必须留到后续阶段再定义

适合原因：

- 与当前阶段自然衔接
- 风险低
- 能直接服务后续真实模块接入

### 优先级 2：开始为 FAST-LIO2 / 后续链路做适配层设计与接口准备

建议内容：

- 明确未来 FAST-LIO2 接入时的 adapter 责任边界
- 明确与现有 `pointcloud_to_maptile_adapter` 的关系：哪些是过渡层，哪些是未来应替换点
- 明确需要补哪些接口文档、launch 参数约定和验收清单

适合原因：

- 能为后续真实链路接入提前扫清接口层面的歧义
- 仍然属于轻量设计与准备工作，不会立刻把任务边界推到重型集成

### 优先级 3：整理下一阶段的验收与证据提交口径

建议内容：

- 提前定义下一阶段的最小验收项
- 明确保留哪些 benchmark / summary / 测试入口
- 明确新增工作不应破坏哪些已有链路和文档结论

适合原因：

- 可以降低后续阶段“边做边改验收口径”的风险
- 便于自我回顾、汇报和答辩衔接

## 当前明确暂不做

下一阶段开始前，以下内容仍然明确暂不做：

- 真实双机联调
- Discovery Server 正式实验
- Chrony 时钟同步正式实验
- FAST-LIO2 正式链路接入与调通
- Nav2 正式链路接入与调通
- 机械臂正式链路接入与调通
- 把当前局部、scan-aligned MapTile 实验包装成全局融合地图
- 新增重型依赖或大规模重构

## 建议的阶段入口约束

下一阶段建议继续遵守下面的工作方式：

- 优先单机、优先可复现、优先可审阅
- 优先接口梳理、适配层设计、验收口径整理
- 每次推进都要明确“当前新增内容是否仍保持现有基线链路不被破坏”
- 若要进入真实双机或重型集成，应作为新的明确阶段单独立项，而不是自然滑入

## 一句话计划摘要

下一阶段建议先围绕现有工程骨架继续做局部 MapTile 链路的下游接口梳理与未来适配层准备，在保持单机、可复现、可验收的前提下，为 FAST-LIO2 和后续真实链路接入建立清晰入口，但暂不直接进入真实双机和重型集成。
